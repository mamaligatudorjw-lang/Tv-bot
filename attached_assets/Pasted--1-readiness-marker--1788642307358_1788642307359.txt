# Сводка открытых проблем — для передачи разработчику

## 1. Основная проблема: readiness marker не подтверждается ни в одном виде

Ожидались (взаимоисключающие) строки от `scripts/start-production.sh`:
```text
[start-production] Flask bot is ready.
```
или
```text
[start-production] WARNING: Flask bot did not become ready within 75s
```

**Ни одна из них не найдена в полном deployment log**, хотя с момента старта artifact (`20:28:36.233`) до первого рабочего polling-цикла (`20:30:08.454`) прошло **~92 секунды** — то есть 75-секундный deadline readiness-проверки заведомо уже истёк к этому моменту. Отсутствие обеих строк логически не должно быть возможным при нормальной работе скрипта.

## 2. Что уже исключено как причина

- **Арифметика deadline** — исключена: реальный интервал polling ~20s (не 75-80s, как предполагалось раньше), но время до первого цикла (92s) всё равно превышает 75s deadline.
- **Третья логическая ветка / баг выхода без print** — не найдена: success-ветка (`curl /ping` успешен → echo), timeout-ветка (deadline истёк → echo warning) покрывают все случаи; ошибки `curl` находятся внутри `if`, `set -e` не приводит к раннему выходу shell.
- **Race при конкурентной записи в общий stdout** — протестирована и исключена: изолированный тест с двумя background-процессами, каждый пишет по 1000 строк в унаследованный общий stdout, дал `malformed=0`.
- **Сам механизм readiness-check в изоляции** — работает корректно: smoke test с искусственной задержкой Flask `/ping` на 52s воспроизвёл ожидаемый `Flask bot is ready.`

## 3. Более широкая и более серьёзная находка: непоследовательные пропуски строк в deployment logs

В разных deployment traces пропадает **разный набор** соседних строк одного и того же линейного bash-скрипта:

- Пример 1: есть `Starting Node API server on :8080`, `Flask bot PID=21`; нет `Starting Flask Telegram bot on :5000`, `Node API PID=...`, `Waiting for Flask bot to be ready ...`.
- Набор пропавших строк **меняется между отдельными запусками** одного и того же кода.

Это не похоже на баг конкретной ветки кода (уже исключено выше) и не на классическую гонку stdout (тоже исключено тестом). Наиболее вероятная граница проблемы — **сбор/маршрутизация/агрегация deployment-логов на уровне платформы**, а не сам код приложения или скрипта.

**Почему это важно за пределами одного readiness-чекпоинта:** весь процесс review в этом проекте (BE-деплой, TP_COUNT=5, multi-TP flag) многократно опирался на "grep production log → ошибок нет → всё чисто" как доказательство. Если строки логов могут непоследовательно пропадать на уровне платформы, то отсутствие ошибки в логе — более слабое доказательство, чем предполагалось на предыдущих этапах. Это не значит, что что-то было пропущено ранее, но точность прошлых "чистых окон" стоит держать в уме с этой оговоркой.

## 4. Что нужно от разработчика

1. **Разобраться с deployment log pipeline** — почему разные запуски одного скрипта теряют разные подмножества строк одного потока. Это платформенный вопрос (log shipping/aggregation), а не логика bash-скрипта.
2. **Альтернативный способ подтверждения readiness**, не зависящий от stdout-логов платформы — например:
   - писать readiness-статус в файл на диске, который можно прочитать напрямую;
   - отражать состояние Flask readiness в теле ответа `/api/healthz` (Node может опрашивать Flask сам и включать это поле в свой health response);
   - любой источник данных, не проходящий через потенциально lossy log capture.
3. Пока это не решено — **инфра-чекпоинт не закрыт**, повторный Publish не делается, `multi-TP` и `BE` остаются `off`.

## 5. Текущее безопасное состояние (без изменений)

- Код после последнего Publish не менялся.
- `BYBIT_DEMO_MULTI_TP_ENABLED=false`.
- `BYBIT_DEMO_BREAKEVEN_ENABLED` не установлен (off).
- Bybit polling и торговая логика продолжают работать штатно (12+ циклов `status=ok`, `tp_setup status=disabled`) — сама проблема ограничена наблюдаемостью деплоя, не влияет на текущее (неактивное для multi-TP/BE) поведение бота.
