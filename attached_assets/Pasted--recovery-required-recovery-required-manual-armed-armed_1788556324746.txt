Разделение состояний (`recovery_required` / `recovery_required_manual` / `armed` / `armed_partial_manual` / `recovery_abandoned`) чёткое и не оставляет пересечений. Отдельный HTTP endpoint с dedicated token через `hmac.compare_digest`, не переиспользующий read-only `STATUS_API_TOKEN`, — правильное решение, учитывая, что это будет реальная торговая операция после включения флага. Решение не делать auto-replan с отменой уже размещённых legs в рамках #199 (вариант B.2) — согласен, это правильно ограничивает scope; полноценный safe replan-with-cancel действительно заслуживает отдельной задачи.

Один существенный пробел, который нужно закрыть перед "да":

## Deadline и manual recovery

`_ensure_tp_orders_for_ledger()` содержит:

```python
if now > int(submitted_ts) + int(BYBIT_DEMO_TP_SETUP_DEADLINE_SEC):
    ...
    return {"status": "recovery_required", ...}
```

Ledger попадает в `recovery_required_manual` уже **после** того, как автоматика (или оператор) это заметила — то есть almost гарантированно уже сильно позже 60 секунд от `ts_submitted`. Если recovery-путь будет вызывать тот же `_ensure_tp_orders_for_ledger()` напрямую — он немедленно упрётся в deadline-проверку и никогда не дойдёт до реального lookup/create, независимо от того, что оператор сознательно инициировал восстановление вручную. Deadline имеет смысл только для **автоматического** unattended re-select, не для явного ручного действия.

Нужно явно решить: recovery-путь либо вызывает отдельную функцию (например, переиспользующую `_place_tp_leg` и lookup-логику напрямую, без deadline-гейта), либо `_ensure_tp_orders_for_ledger()` получает параметр типа `ignore_deadline=True`/`manual=True`, который явно отключает эту проверку только для operator-initiated вызовов. Без этого решения вся фича физически не сможет сработать ни разу.

## Мелкие уточнения, не блокируют "да", но нужны в diff'е

- Recovery-путь должен переиспользовать существующий `_place_tp_leg()` (lookup-then-create, taxonomy ошибок) для каждой недостающей ноги, а не дублировать эту логику — подтверди на этапе diff.
- Уже успешно размещённые legs (`order_id` есть) после перехода в `armed_partial_manual` должны продолжать штатно попадать в `reconcile_tp_legs()` (обычный poll) — добавь короткую проверку/тест, что смена `protection_state` на `armed_partial_manual` не выключает их из обычного read-only reconciliation.
- Есть ли какая-то защита от brute-force попыток подбора `BYBIT_DEMO_TP_RECOVERY_TOKEN` (rate limit / хотя бы логирование неудачных попыток авторизации)? Не обязательно для этой задачи, но если легко добавить — сделай; если нет, просто подтверди, что полагаемся исключительно на секретность токена.
