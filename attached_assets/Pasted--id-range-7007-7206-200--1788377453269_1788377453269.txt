Ключевая деталь в ваших же данных, которую стоит дожать: **id range 7007–7206 при 200 возвращённых строках — это ровно 200 id без единого пропуска** (7206 − 7007 + 1 = 200). А диапазон времени (28.08 03:11 → 02.09 19:22) полностью накрывает целевое окно.

Отсюда следует вывод, для которого деплой уже не нужен:

- если бы строка `alerts` была вставлена и **осталась** — она была бы в этих 200 (по ts и по id) → её нет;
- если бы строка была вставлена и **удалена** (любой из rollback-путей 7366/7387/7397) — в id-последовательности остался бы **пропуск** → пропусков нет.

Значит `send_alert_with_log` **не дошла до INSERT на строке 7299** ни для одного из трёх событий. Это снимает мою гипотезу об исключении после commit — она мертва. Разрыв находится строго между warning на 7196 и INSERT на 7299.

В этом промежутке все `return`-ветки логируют (`Suppressed` ×4, `polling_side_effect_blocked` ×1 — всё искали, 0). Остаётся ровно одна незащищённая точка:

```python
body_text = _append_btc_regime_enrichment(
    body_text, alert_type, recommendation
)
```
(строки 7273-7275 — не обёрнуто в try/except, стоит прямо перед INSERT)

Проверяю, есть ли у неё внутренняя защита:

Стоп — должен **отозвать собственный вывод** про id-пропуски, пока не проверю схему. В SQLite при `INTEGER PRIMARY KEY` **без `AUTOINCREMENT`** удалённый максимальный rowid **переиспользуется** следующей вставкой, то есть insert-then-delete не оставляет дырки. Мой аргумент верен только при `AUTOINCREMENT`. Проверяю:

Схема подтверждает: `id INTEGER PRIMARY KEY AUTOINCREMENT` (app.py:5764). При `AUTOINCREMENT` SQLite **никогда не переиспользует** удалённые id — значит пропуск остался бы навсегда. Мой вывод устоял:

**200 строк на ровно 200 последовательных id (7007–7206) ⇒ в этом диапазоне не было ни одной удалённой строки ⇒ для трёх событий INSERT в `alerts` (строка 7299) не выполнялся вообще** — ни с сохранением, ни с последующим откатом.

## Получается логическое противоречие

Между warning на 7196 и INSERT на 7299 **не осталось ни одной немой ветки**:

| Точка | Что делает | Статус |
|---|---|---|
| 7204-7222 открытая позиция | логирует `Suppressed` | искали → 0 |
| 7225-7230 не LONG/SHORT | логирует `Suppressed` | здесь всегда "LONG" |
| 7238-7243 score < min | логирует `Suppressed` | искали → 0 |
| 7246-7255 BULL/SHORT | только для SHORT | не наш случай |
| 7257-7264 потолок LONG | логирует `Suppressed` | искали → 0 |
| 7273-7275 BTC enrichment | **внутри полный try/except** (5619-5634), выбросить не может | исключено |
| 7294 alert_insert | логирует `polling_side_effect_blocked` | искали → 0 |

То есть **кодового пути, который молча съедает сигнал в этом участке, не существует**. Значит неверна не логика — неверна посылка: что warning и его исход должны лежать в одном и том же логе.

## Наиболее вероятное объяснение теперь — расщепление источника логов

Вы сами раньше зафиксировали: параллельно с published deployment работал **второй, workspace-процесс** (позже остановлен). `bot_debug.log` — файл в рабочей директории, то есть, скорее всего, лог **workspace**-процесса, тогда как published-процесс пишет в отдельный log service, чья история до 19:02 не сохранилась. Тогда 17 совпали потому, что обе строки попали в один сток, а 3 «потерялись» потому, что их продолжение ушло в другой.

## Два шага, оба без деплоя и без нового SQL

1. **Трассировка по `cycle_id`, а не по времени.** `_CycleLogFilter` (app.py:120-147) добавляет префикс `cycle_id=...` ко всем строкам, содержащим маркеры — включая `overheated_24h`, `Demo `, `alert_delivery`, `Telegram send`. Значит каждый из 20 warning'ов должен нести свой `cycle_id`. Возьмите `cycle_id` тех трёх и выгребите **все** строки с этим же `cycle_id` — это даст реальную последовательность выполнения цикла, а не окно ±120 с. Если после warning в этом цикле вообще нет строк — цикл оборвался/писал в другой сток; если есть — увидим, где именно.
2. **Проверка PID.** Строки `Demo ...` и `Demo DUPLICATE BLOCKED` несут `pid=%d`. Посмотрите, сколько разных PID пишут в `bot_debug.log` в интервале 18:00–18:30. Если больше одного — подтверждается дублирующийся рантайм и расщеплённая картина; если ровно один — надо понять, тот ли это процесс, что породил warning.
