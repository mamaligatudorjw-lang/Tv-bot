152 — Частичный TP 50% + trailing на остаток
(Идея B. #151 не запускается — bootstrap CI показал, что trailing-лифт из #150 не выделяется на фоне соседних шагов грида, forward-окно не потрачено.)
What & Why
Механика: вход/SL/TP — как сейчас (без изменений). При достижении TP закрывается 50% позиции по цене TP (фиксация прибыли), для оставшихся 50% убирается фикс. SL и ставится trailing stop с полом на уровне TP — вторая половина не может закрыться ниже цены TP, риск ограничен тем, что уже гарантировано первой половиной. Если TP не достигнут — поведение идентично текущему baseline, механика не активируется.
Подтверждённые определения
	•	Пол trailing: уровень выхода второй половины не может быть ниже цены TP.
	•	Доля частичного закрытия: 50%, фиксирована — не грид-серчится.
	•	Грид по trailing-проценту на остатке: 2/3/4/5/6/8/10% — тот же, что в #150, для сравнимости.
	•	Область первого прохода: только overheated_24h. ema_cross_confirmed исключён — его лестница подтверждений (TP-множитель 2.0×→1.5×→1.0× по уровням) требует отдельно определённой семантики (применять идею B к финальному выходу лестницы или к каждому уровню) прежде, чем включать эту стратегию. Оформляется отдельным следующим шагом после #152.
	•	Forward-окно: не расходуется на этом этапе — используется тот же frozen in-sample набор, что и в #150/#136.
Методология
	1.	Baseline: полное закрытие 100% на TP (как сейчас), на in-sample наборе overheated_24h.
	2.	Тест: частичное закрытие 50% на TP + trailing с полом на TP на остатке, по гриду шагов.
	3.	Метрики как в #150: n, ΣR, WR, avg R — отдельно для baseline и для каждого шага грида.
	4.	Bootstrap CI сразу в этом же прогоне (не отдельным письмом постфактум, как было с #150/#151): ресемплинг по уникальному signal ID, CI по всем шагам грида, не только по «победителю»; те же критерии на пересечение нуля и перекрытие с соседними шагами.
	5.	Явно показать долю сигналов, дошедших до TP (только они участвуют в развилке), от общего числа baseline-сигналов.
Done looks like
	•	Read-only CLI-отчёт, не трогает production/SQLite — как в #150.
	•	Per-signal audit: strategy, direction, дошёл ли до TP, цена TP-триггера, дальнейшая траектория до trailing-выхода, итоговый R по сумме двух половин.
	•	Grid summary с n/ΣR/WR/avgR по каждому шагу + bootstrap CI по каждому шагу.
	•	Явная пометка in-sample, не основание для production или forward-shadow записей.
	•	Тесты: пол trailing на уровне TP (нельзя закрыть вторую половину ниже TP), сигналы без касания TP не попадают в тестовую ветку, read-only.
