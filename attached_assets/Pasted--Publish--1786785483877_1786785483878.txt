Однозначный ответ по базе — до нажатия Publish

Ты дал два взаимоисключающих утверждения о том, что происходит с базой при публикации:

	•	в предыдущем ответе: «При republish VM получает свежую копию из workspace, текущая база перейдёт в продакшен без потерь»;
	•	в этом: «Reserved VM — persistent storage, alerts.db на VM не перезаписывается dev-версией — VM сохраняет свою базу».

Нужен один определённый ответ, проверенный по документации Replit, а не по предположению: перезаписывается ли файл alerts.db на Reserved VM при публикации новой версии кода. От этого зависит порядок действий, и ошибка здесь необратима.

1. Перед публикацией — сохранить dev-базу. Скопируй текущий alerts.db из рабочей среды в резервный файл с датой в имени. Это бесплатно и защищает от любого исхода: в ней 1285 позиций и все поля, которые мы добавляли за эти дни (exit_method, source_demo_id, маркеры отсечки). Именно по ней сделан весь анализ.

2. Признай, что маркеры отсечки не работают для базы VM. OVERSOLD_DURATION_FILTER_TS, MONITOR_FIX_SINCE, CONFLUENCE_CAP_CUTOFF_TS, OVERSOLD_SL_CAP_SINCE — это моменты деплоя в dev. В базе VM в те же моменты работал другой код, поэтому разбивка «до/после» по ним для данных VM ничего не значит. Разборы 26 августа и 3 сентября по этим меткам дадут мусор.

Вместо них введи одну новую константу — UNIFIED_START_TS с моментом публикации. После перехода на единый процесс это будет единственная честная точка отсчёта: всё, что до неё, — история двух параллельных ботов с разным кодом; всё, что после, — чистые данные одной системы. В /demo и /scorestats добавь предупреждение, если выборка захватывает период до этой даты.

3. Порядок действий подтверждаю, но с уточнением по шагу 0. Сравнение открытых позиций dev и VM делать не нужно — dev-позиции по определению принадлежат другому боту с другим кодом, тянуть их в VM смысла нет, они только смешают данные. Достаточно резервной копии базы из пункта 1.

Дальше: Publish → проверить /status и один цикл сигналов → убедиться, что check_demo_positions больше не зависает в логах VM → остановить dev-воркфлоу.

4. После остановки dev-воркфлоу подтверди одной строкой: уведомления в Telegram идут только из одного процесса, дублей больше нет.
