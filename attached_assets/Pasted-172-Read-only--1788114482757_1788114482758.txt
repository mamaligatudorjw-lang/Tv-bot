172 (номер уточнить у дева) — Read-only скан истории: «памп → коррекция → снятие лонгов → крупные сделки на 5м → возврат к уровню поддержки»
What & Why
Новая гипотеза паттерна (не пересекается с overheated_*/ema_cross*), проверить на истории до любого решения о включении в стратегии:
	1.	Монета резко растёт (памп).
	2.	После пампа — коррекция.
	3.	Коррекция снимает (ликвидирует) многих лонгистов — по реальным данным ликвидаций, не по прокси (фитиль+объём).
	4.	На 5-минутном таймфрейме после этого виден вход крупных сделок (крупный покупатель/покупатели).
	5.	Далее цена вновь высоко растёт — успех = возврат цены на уровень поддержки (какой именно уровень — см. ниже, нужно зафиксировать).
Это read-only exploratory задача, как #150-171 — цель понять, есть ли вообще статистически значимый эффект, прежде чем это станет кандидатом в стратегию. Никакого влияния на production/whitelist/scoring на этом этапе.
Confirmed
	•	Скан широкий — топ монет по объёму/волатильности, не ограничен текущим whitelist бота (overheated_*, ema_cross*).
	•	Метрика успеха — возврат цены на уровень поддержки (не «+5% за N часов» и не «полный возврат к максимуму»).
	•	Метод определения снятия лонгов — реальные данные по ликвидациям, не прокси.
Критично проверить до начала реализации (feasibility gate)
Глубина исторических данных по ликвидациям — под вопросом, и это может определить, реализуема ли задача вообще в заявленном виде:
	•	У большинства бирж (Bybit, Binance и т.п.) публичный API отдаёт ликвидации только как realtime-поток (например, WebSocket force-order feed) — глубокого REST-архива ликвидаций за месяцы/годы обычно нет.
	•	Нужно явно проверить: есть ли у бирж, с которыми уже работает бот (Bybit, Gate.io), исторический архив ликвидаций на нужную глубину периода скана.
	•	Если нет — варианты (описать в ответе, не решать самостоятельно молча):
	•	(a) ограничить скан коротким окном, где реальные данные фактически доступны;
	•	(b) сторонний агрегатор с API (например, Coinglass) — если это не выходит за рамки бюджета/лицензии;
	•	(c) откат к прокси (резкий фитиль вниз + аномальный объём) — только как явно помеченный компромисс, если (a)/(b) не подходят, не как тихая подмена того, что просили.
Не начинать реализацию, пока feasibility по ликвидациям не подтверждена — иначе есть риск потратить работу на метод, для которого просто нет данных на нужную глубину истории.
Параметры, которые сейчас не зафиксированы — нужно предложить дефолты и подтвердить
Формулировка «резко выросла», «коррекция», «крупные сделки» пока не операционализирована. Предлагаю зафиксировать явно (числами), а не оставлять на усмотрение реализации:
	1.	Памп: порог роста за окно (например, +N% за M часов на 15м/1ч свечах).
	2.	Коррекция: порог отката от локального хая пампа (например, −K% от пика).
	3.	Снятие лонгов: порог объёма ликвидаций лонгов (абсолютный или относительно среднего по монете), совпадающий по времени с коррекцией.
	4.	Крупная сделка на 5м: нужно определить метод — отдельная сделка выше $-порога на трейд-ленте (aggTrades) vs аномальный объём 5м-свечи относительно скользящего среднего. Это разные технически (и по стоимости получения истории) подходы — зафиксировать один.
	5.	Уровень поддержки для критерия успеха: какой именно уровень — цена начала коррекции, база до пампа, иной технический уровень. Без этого «возврат на уровень поддержки» неоднозначен и по-разному даст разные n/WR.
	6.	Окно ожидания исхода: сколько времени даём паттерну на возврат, прежде чем считать «не сработало» (по аналогии с fixed-window resolve, как в #150/tp_vs_sl-анализе, а не «ждём сколько угодно»).
Done looks like
	•	Ответ по feasibility ликвидационных данных до реализации скана (см. выше) — с явным указанием, какой из вариантов (a/b/c) применяется и почему.
	•	Предложенные дефолты по пп. 1-6 выше, на согласование, прежде чем фиксировать финальную версию скана.
	•	Read-only отчёт (Markdown/CSV): найденные исторические случаи (монета, даты каждой стадии паттерна, объём ликвидаций, объём крупной сделки, исход — достиг/не достиг уровня поддержки, время до исхода), плюс агрегат (n случаев, % успеха, если объём данных позволяет — CI/эффект по аналогии с прошлыми отчётами; при малом n — просто список случаев без статистики, честно помеченный как insufficient для выводов).
	•	Никаких изменений в production, scoring, whitelist, стратегиях бота.
Out of scope
	•	Включение паттерна в реальную/демо-торговлю — отдельное решение после review отчёта.
	•	Прокси вместо реальных ликвидаций — только если feasibility подтвердит, что реальных данных нет на нужную глубину, и явно согласовано как компромисс.
	•	Расширение на другие критерии успеха («+X% за Y часов» и т.п.) — зафиксирован один: возврат на уровень поддержки.
