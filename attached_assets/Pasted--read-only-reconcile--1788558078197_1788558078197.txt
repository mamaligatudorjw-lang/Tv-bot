Хорошо структурированный план, использующий все накопленные паттерны (read-only reconcile остаётся чистым, отдельный write-hook, readback-подтверждение вместо доверия к самому API-ответу, explicit terminal states с audit). Есть четыре пункта, которые нужно закрыть перед реализацией.

## 1. В eligibility нет проверки `be_state`

П.2 перечисляет условия допуска (`protection_state`, наличие TP1, `executed_qty > 0`), но не включает `be_state == not_armed` как фильтр. Без этого `ensure_breakeven_sl()` будет пере-вызываться на **каждом** poll cycle даже для уже `armed` ledger — п.3 защищает от ухудшения SL и от лишнего API mutation ("можно сразу подтвердить armed... без лишнего API mutation"), но сам `get_position()`-readback всё равно будет выполняться заново каждый цикл навечно. Это не риск безопасности, но прямое повторение того самого паттерна, который мы уже исправляли в #199 (`_ensure_tp_orders_for_ledger` теперь явно исключает уже-`armed`/`armed_partial_manual`/`recovery_abandoned` ledger из повторной обработки). Добавь `be_state in {"not_armed"}` (или `!= "armed"`) как явный фильтр в eligibility, а не полагайся только на "already better protected" проверку внутри.

## 2. Не описано взаимодействие с активным reversal

П.2 исключает "opposite-direction position после reversal" — это покрывает случай **после** завершённого reversal. Но что если reversal **в процессе** (ledger уже помечен как имеющий активный/pending reversal — `_run_reversal_close()` может в этот самый момент отменять TP legs или готовить reduce-only close) в момент, когда `ensure_breakeven_sl()` решает переставить SL? Два независимых mutation-пути (BE amend SL и reversal close) могут гоняться друг за другом на одной позиции. Нужна явная eligibility-проверка "у ledger нет активного/незавершённого reversal" (по аналогии с тем, как #199 проверяет terminal-состояния), а не только "уже развернулась".

## 3. Подтверди семантику `avgPrice`

П.3 берёт "текущий live avgPrice из get_position()" как источник цены BE. Хочу явно подтвердить понимание: в Bybit V5 `avgPrice` позиции — это weighted average **entry** price, который не меняется при частичных reduce-only закрытиях (TP legs), только при добавлении к позиции. То есть это ровно "entry price" из письма, просто взятый live, а не из локально сохранённого поля — не "средняя цена исполнения TP". Если это осознанная трактовка (а не случайное совпадение терминов) — фиксируй это явно в плане/коде комментарием, чтобы будущий review не спутал это с "average TP exit price".

## 4. Taxonomy ошибок `/v5/position/trading-stop`

П.7 полагается на readback-подтверждение вместо доверия ответу API — это разумно и даже более надёжно, чем taxonomy для order creation/cancel, **потому что** `trading-stop` — идемпотентная SET-операция (не создание нового объекта), так что риск duplicate-создания здесь структурно не существует, в отличие от order create/cancel на этапах 4–5. Согласен, что это снижает необходимость в такой же развёрнутой taxonomy. Но п.7.6 всё равно обещает "deterministic reject не будет бесконечно повторяться" — для этого нужен хотя бы минимальный список реальных Bybit-кодов для этого конкретного endpoint (invalid price, position not found и т.п.), проверенный против официальной таблицы на этапе diff — так же, как мы делали для order/cancel и order/create, просто короче список, раз риск ниже.

После ответа на пункты 1–3 (это уточнения формулировок/логики, не полная переработка) и подтверждения, что п.4 будет закрыт verified-таблицей на этапе diff — готов дать "да" на реализацию.
