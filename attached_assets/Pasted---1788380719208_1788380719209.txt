Стоп. В этом ответе есть **противоречие с уже подтверждёнными данными**, и оно важнее, чем сам пустой результат.

`demo_id_gap_rows` не фильтруется по символу — это срез **всей таблицы** `demo_positions` за окно. Для EGLD окно `1788372090–1788372330`. А в вашем же raw-логе за это окно есть четыре подтверждённых вставки:

| Лог | `ts=` | В окне? |
|---|---|---|
| `Demo shadow: TUSDT LONG/overheated_early` | 1788372242 | да |
| `Demo shadow: FONEUSDT LONG/overheated_early` | 1788372247 | да |
| `Demo shadow: AKEUSDT SHORT/pump_24h_fade` | 1788372267 | да |
| `Demo shadow: GTUSDT LONG/bb_squeeze` | 1788372314 | да |

В `_demo_open_position` логируемое `ts=%d` — это `_ts_recv`, и он же вставляется в `ts_open` (строки 2224, 2263). То есть `demo_id_gap_rows` **обязан был вернуть минимум четыре строки**. Вернул ноль.

Ответ пришёл из **не той базы данных**. Это доказывается вашими же данными, без новых запросов.

## Доказательство

`HIT_RATE_DB_PATH = os.path.join(os.path.dirname(__file__) or ".", "alerts.db")` (app.py:807) — файл БД лежит **рядом с исходником**. У workspace-процесса и у published-VM это два физически разных файла.

Сверка окон с raw-логом:

| Окно | Что лог доказывает внутри окна | Что вернул `demo_id_gap_rows` |
|---|---|---|
| EGLD `1788372090–1788372330` | TUSDT `1788372242`, FONEUSDT `1788372247`, AKEUSDT `1788372267`, GTUSDT `1788372314` — **4 вставки** | `[]` |
| ARB `1788373286–1788373526` | SPACEHOODUSDT `1788373516` | `[]` |
| KITE `1788373303–1788373543` | SPACEHOODUSDT `1788373516` | `[]` |

`ts=` в строке `Demo shadow:` — это `_ts_recv`, он же вставляется в `ts_open` (2224 → 2263). Запрос не фильтрован по символу. Значит он **обязан** был вернуть эти строки. Вернул ноль по всем трём окнам.

Вывод строгий: **база, которую читает published endpoint, не является базой, в которую писал процесс `pid=35`.**

## Что из-за этого отзывается

Мой вывод «непрерывность id 7007–7206 ⇒ строка в `alerts` не создавалась» — **отзываю**. Логика была верна, но применена к published-базе, тогда как события писались в другую. Отсутствие EGLD/ARB/KITE в `/bot-api/signals/recent` этим же и объясняется.

Точно так же обесцениваются все `[]` из forensic endpoint: `ledger_rows`, `reversal_rows`, `demo_rows` — они про другой файл.

Это уже **четвёртый** случай одной и той же ошибки: не тот лог-файл → секционированный срез → старая версия endpoint'а → не та БД. Каждый раз пустой результат читался как отрицательный.

## Что делать дальше — деплой не нужен

Всё решается одним запросом в workspace-shell, к локальному файлу:

```bash
cd telegram-webhook-bot
ls -la alerts.db

# 1. Контроль: есть ли те 4 строки, которые доказаны логом?
sqlite3 alerts.db "SELECT id, symbol, alert_type, is_shadow, ts_open
                   FROM demo_positions
                   WHERE ts_open BETWEEN 1788372090 AND 1788372330
                   ORDER BY id;"

# 2. Собственно ответ по трём кейсам
sqlite3 alerts.db "SELECT id, symbol, direction, alert_type, status, is_shadow, ts_open
                   FROM demo_positions
                   WHERE symbol IN ('EGLDUSDT','ARBUSDT','KITEUSDT')
                     AND ts_open BETWEEN 1788372090 AND 1788373543
                   ORDER BY id;"

# 3. И по alerts — тот же вопрос в правильной базе
sqlite3 alerts.db "SELECT id, ts, symbol, alert_type, score, delivery_ts
                   FROM alerts
                   WHERE symbol IN ('EGLDUSDT','ARBUSDT','KITEUSDT')
                     AND ts BETWEEN 1788372090 AND 1788373543
                   ORDER BY id;"
```

Запрос №1 — обязательный контроль: если он вернёт четыре строки, база правильная и ответам №2/№3 можно верить. Если и он пуст — значит и workspace-файл не тот, и нужно искать, куда вообще писал `pid=35`.

## Отдельно — это находка сама по себе

Два рантайма с **двумя независимыми базами**, торговавшие один и тот же Bybit Demo аккаунт — это не просто исторический казус. Расщепление данных осталось: часть истории сигналов лежит в одном файле, часть в другом, и ни один отчёт по одной базе не полон. Это стоит завести отдельным тикетом, наравне с долговечной телеметрией.
